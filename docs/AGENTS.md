# 개발 및 유지보수 문서 규칙

이 파일은 `docs/` 아래 문서의 작성·갱신 규칙을 정의한다. 루트 `AGENTS.md`에는 루트 바로 아래 항목의 역할만 간결하게 유지한다.

## 문서 구성

고정 문서 5개와 `requirements/`, `screens/`, `changes/`만 사용한다. 고정 문서는 MVP 이후에도 같은 파일을 갱신하며, 버전별로 복사하지 않는다. 아래 구성은 관리 기준이며, 아직 결정되지 않은 내용을 채우기 위해 빈 문서나 추측성 내용을 만들지 않는다.

```text
docs/
├── AGENTS.md                 # 이 디렉터리의 문서 관리 규칙
├── 0-PRODUCT.md
├── 1-SYSTEM-ARCHITECTURE.md
├── 2-DESIGN.md
├── 3-DATABASE.md
├── 4-USERFLOW.md
├── requirements/
│   └── <feature>.md
├── screens/
│   └── <screen>.html
└── changes/
    └── <number>-<change>.md
```

`DATABASE.md`는 이 프로젝트의 번호 규칙에 맞춰 `3-DATABASE.md`로 관리한다. 기능별 문서 디렉터리 이름은 `specs/` 대신 `requirements/`를 사용한다. `OPERATIONS.md`는 만들지 않는다.

## 고정 문서의 책임

| 문서                         | 관리할 내용                                                                                                                  |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `0-PRODUCT.md`             | 제품 목적, 대상 사용자, 해결할 문제, 전체 범위와 제외 범위, 제품 공통 정책. 기능 상세는 요구사항 문서로 연결한다.                                                    |
| `1-SYSTEM-ARCHITECTURE.md` | 기술 스택, 모듈 역할과 경계, 시스템 간 데이터 흐름, 외부 서비스 연동, 주요 기술 선택의 이유. 개발·유지보수에 필요한 실행·테스트·배포 명령과 환경변수의 이름·용도도 여기에 둔다. 비밀값은 기록하지 않는다. |
| `2-DESIGN.md`              | 공통 UI/UX 원칙, 디자인 토큰, 컴포넌트와 상태, 반응형·접근성 기준. 기능별 화면의 동작은 요구사항 문서로 연결한다. 디자인 원칙은 수정/편집하지 않고 그대로 사용한다.                      |
| `3-DATABASE.md`            | 엔티티·테이블과 관계, 주요 필드의 의미, 키·제약조건·인덱스, 데이터 보관·삭제 정책. 실제 스키마·마이그레이션 파일을 연결하며, 전체 스키마를 중복 전사하지 않는다.                          |
| `4-USERFLOW.md`            | 주요 사용자 여정, 진입점과 종료점, 화면 간 이동, 인증·권한에 따른 분기와 주요 실패·복구 경로. 기능별 세부 조건은 요구사항 문서로 연결한다.                                      |

## 기능 요구사항: `requirements/`

- 기능별로 하나의 문서를 유지하며, 변경할 때 기존 문서를 갱신한다.
- 목적, 사용자에게 제공할 동작, 업무 규칙·권한, 예외 처리, 완료·테스트 기준을 기록한다.
- 필요한 API 계약과 기능별 화면·상태 설명도 해당 문서에 포함한다.
- 고정 문서에 있는 공통 기준은 링크하고 중복해서 적지 않는다.
- 현재 동작과 확정된 예정 동작을 구분한다. 미확정 아이디어를 현재 요구사항으로 기록하지 않는다.

## 화면 정의서: `screens/`

- 화면마다 HTML 파일 하나를 유지하며, 변경할 때 기존 파일을 갱신한다.
- 화면의 배치와 모양만 보여 준다. 화면 동작·상태·업무 규칙은 해당 기능 요구사항 문서에 두고, 요구사항 문서에서 화면 파일로 링크한다. `4-USERFLOW.md`의 화면 간 이동에서도 화면 파일로 링크한다.
- 파일 하나로 완결한다. 스크립트를 넣지 않고, 외부 파일을 불러오지 않는다. 색·글꼴·간격은 `2-DESIGN.md`의 토큰을 쓴다.
- 컴포넌트마다 `data-component="<이름>"`을 붙인다. 이름은 파일 안에서 유일하고 영문 소문자·숫자·`-`만 쓴다. 수정 요청과 부분 교체의 기준이 된다.
- 화면 크기를 `<html data-frame="…">`로 밝힌다. `mobile`은 390×844 고정 프레임이다. `page`는 폭 1280–1440 기준의 유동 레이아웃이고, 휴대폰 폭에서도 메뉴가 쌓이고 넓은 표는 상자 안에서 스크롤되게 만든다. 없으면 `page`로 본다.
- 다른 화면으로 가는 버튼·링크는 `<a href="<화면>.html">`(같은 `screens/` 폴더 기준 상대 경로)로 연결한다. 화면 파일을 클릭해 넘겨 보는 프로토타입이 된다.
- 모르는 값은 지어내지 않고 `[가격]`처럼 자리표시로 둔다. 의미 없는 채움 글(lorem ipsum)과 지어낸 수치를 쓰지 않는다.
- 실제 요소를 쓴다 — 누르는 것은 `<button>`·`<a href>`, 입력은 `<input>`과 `<label>`. 아이콘만 있는 버튼에는 `aria-label`을 붙인다. 글자 대비는 4.5:1 이상(24px 이상은 3:1)이고, 구별해야 하는 색은 색상만이 아니라 밝기도 다르게 한다.
- 디자인 문서에 없는 장식(배경 그라데이션, 이모지 아이콘, 왼쪽 굵은 테두리 카드)을 넣지 않는다.

코딩 에이전트는 화면 파일을 이렇게 읽는다.

- 배치·모양·문구의 기준이다. 색·글꼴·간격은 HTML 값을 베끼지 않고 `2-DESIGN.md`의 토큰으로 구현한다.
- `data-component` 이름은 구현할 컴포넌트 이름의 후보다.
- 화면 간 링크는 이동 흐름을 보여 준다. 동작·상태·검증 규칙은 해당 기능 요구사항 문서가 우선한다.

## 변경 기록: `changes/`

- MVP, 신규 기능, 기존 동작·정책 변경, 중요한 구조 변경을 작업 단위로 기록한다.
- 변경 이유, 범위와 제외 범위, 관련 문서 링크, 구현 작업, 검증 방법·결과, 진행 상태를 기록한다.
- 상태는 `예정`, `진행 중`, `완료`로 구분한다. 완료 시 실제 반영 범위와 결과를 확정한다.
- 완료된 기록은 당시 결정과 결과로 보존한다. 후속 변경은 새 기록을 추가한다.
- 요구사항에 맞게 코드를 고치는 작은 버그 수정은 이슈나 PR 기록으로 충분하다. 문서가 잘못된 경우에만 관련 내용을 수정한다.

## 변경 시 관리 순서

1. 작업 전에 관련 고정 문서와 기능 요구사항을 확인한다.
2. 요구사항·구조가 달라지는 작업은 변경 기록에 범위와 검증 기준을 정리한다.
3. 개발 전에 확정된 변경을 관련 문서에 반영하고 `예정` 또는 `진행 중`임을 표시한다. 기존 동작과 혼동되지 않게 한다.
4. 구현과 검증 후 문서를 실제 반영 상태에 맞추고, 변경 기록에 결과를 남긴다. 출시가 별도라면 출시 전까지 예정 표시를 유지한다.
5. 영향받는 문서만 갱신한다. 현재 기준은 고정 문서와 `requirements/`, `screens/`, 과거 변경의 이유와 결과는 `changes/`에서 확인한다.

별도 PRD·API 명세·테스트 계획·ADR·로드맵·운영 문서를 추가하지 않는다. 제품 정의는 `0-PRODUCT.md`, API와 테스트 기준은 기능 요구사항, 현재 기술 선택은 아키텍처, 변경 결정과 예정 작업은 변경 기록에 포함한다.

## TaskReporter 런타임 예외

`docs/inprogress/`는 basic-team 및 office-basic-team의 실행 중 진행 HTML, run sidecar와 폴백 전체 상태를 보관하는 예외다. 제품·요구사항·화면 정의의 기준 문서로 사용하지 않는다. 기존 실행 파일을 문서 정리 과정에서 수정하거나 삭제하지 않는다. `screens/`는 실제 화면 정의 HTML이 필요할 때만 만들며 현재 구현 화면은 React 소스와 요구사항에서 확인한다.

루트 `PRODUCT.md`와 `DESIGN.md`는 도구 호환성을 위한 안내 파일이며, 현재 기준은 각각 `0-PRODUCT.md`, `2-DESIGN.md`다.
