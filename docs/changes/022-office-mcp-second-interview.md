- 작업과 TODO를 끝까지 감사할 수 있었다. 현재 `get_run`과 기존 최종 감사에 61개 task·258개 TODO가 남아 있고 최종 미완료·미입력 model/effort가 없다. 종료 시각은 `2026-10-23T19:02:12.475Z`다.

- 체크인 답변이 실제 작업 설명을 보존했다. 12개 checks는 모두 answered이며, 구현·브라우저 검증·팀 통합이 남았을 때 미완료 TODO를 유지한 답변이 있다. 지연 경고를 없애려고 가짜 완료로 바꾼 사례로 보지 않는다.

회고 집계의 평균 check 회신 간격은 46.579초다. 생성·회신 저장 시각의 차이이며 MCP 응답 속도나 알림 전달 시간을 측정한 값이 아니다. `todos_ticked_at_close=109/258`은 task 종료 patch에서 체크됐다는 뜻이다. 실제 작업을 늦게 보고했다거나 run 마지막에 몰아서 처리했다는 증거는 아니다.

## 불편과 원인 판별

### 같은 프로젝트에서 어느 실행을 보고 있는지 혼란

상대는 사용자가 기존 작업의 층을 덮었다고 지적한 경험을 보고했다. 보존된 retro도 같은 혼선을 기록한다. 초기 run은 실제 cwd를 project_path로 사용했고, `중단 전용 층으로 보고 위치 이동`으로 종료했다. 이후 별도 reports 경로에 새 run을 만들었다. 초기 PLAN의 note는 구현 취소가 아님을 명시하며 미완료 TODO도 보존했다.

이는 사용자 혼선과 우회를 입증한다. 다른 실행의 DB 데이터를 삭제·덮어썼다는 증거는 아니다. 현재 서버는 run_id 단위로 갱신하고 다른 프로젝트의 run_id를 거부한다. 웹은 프로젝트 진입 시 최근 보고된 진행 run을 선택하며 진행 run 선택기도 이미 있다([서버](../../server/app.ts), [웹](../../web/src/App.tsx)). 따라서 개선 대상은 실행 식별과 선택을 더 명확히 하는 것이다. 당시 우회처럼 reports 경로를 새 프로젝트로 만드는 방식을 일반 해법으로 권장하지 않는다. 실제 프로젝트 경로를 유지하면서 독립 run과 기존 run 재개를 구분해야 한다.

020과 같은 작업 공간에서 생긴 연관 사건이므로, 독립된 사용자 두 명에게 반복됐다는 통계로 부풀리지 않는다. `get_retros`의 해당 경로 집계는 run_count=1·candidate=false이며 경로 이동으로 회고가 분산될 수 있다.

### planner·임시 자리와 실제 작업 상태를 이해하기 어려움

상대는 사용자가 planner가 가만히 있다고 했고 임시 자리의 캐릭터가 누구인지 물었다고 답했다. 후속 확인에서도 당시 화면·발언의 정확한 시각과 task 대응, 새 run 생성 전후는 특정하지 못했다. 최종 데이터에는 초기 Planner/Architect/Critic과 후속 `plan-global-*` 등 계획 카드가 따로 남아 있다. 완료한 초기 planner가 서 있는 것만으로 후속 계획이 없었다고 판단할 수 없다.

후속 답변과 기존 `final.md:63`을 직접 대조한 결과, 당시 임시 자리에 표시된 `대표 · 나`는 사용자 아바타이며 팀의 추가 작업자가 아니었다. 이 관찰을 unknown owner 오류로 분류하지 않는다. 사용자 아바타와 보고된 작업자의 차이가 더 명확해야 한다는 UX 후보로 남긴다. 이번 조사에서 화면을 재현하지는 않았다.

현재 데이터에 후기 리뷰 카드 9개의 owner가 `review-karpathy`, `review-ponytail`, `review-impeccable`, `review-e2e`로 남아 있다. 현재 [역할 레지스트리](../../shared/roles.json)는 `reviewer-*`와 정확한 외부 reviewer 이름을 인식하며 `review-*`는 인식하지 않는다. 해당 카드의 `lane`은 `review`라 plan 우선 배정도 적용되지 않아 현재 resolver에서는 임시 자리로 간다. `reviews[]`에는 별도로 `Karpathy Agent` 등 네 정식 이름이 있어 추가 캐릭터가 생길 조건도 있다. 이 데이터 조건은 확인했지만 당시 사용자가 본 모든 임시 캐릭터와의 일대일 대응이나 당시 렌더링 버그를 입증하지는 않는다.

Office owner는 표시 키이고 native agent handle은 실제 실행 식별자다. 카드의 `진행중`과 애니메이션을 실제 프로세스 생존·현재 실행의 증거로 대신할 수 없다. 현재 설치된 basic-team의 `references/office-operations.md`에도 이 구분과 라운드 간 정식 reviewer owner 재사용 규칙이 이미 있다. 규칙을 새로 쓰기보다 첫 보고의 배정 확인과 준수 여부 검증이 우선이다.

### 추가 요구가 기존 작업에 어떻게 반영되는지 추적하기 어려움

상대는 공통 안내·기존 상품 재전송·선택 피드백으로 요구가 늘면서 사용자가 계획 반영, 기존 팀 재사용, 기존 작업 중단 여부를 반복 확인했다고 답했다. 후속 답변이 제시한 사용자 원문은 “추가 요구사항하는 것들은 계획 세우게하면서 하고있지 ?”와 “기존에 하던 작업들은 병렬로 계속 안해도돼 ? 멈춰야하는 일이야 ?”다. 직접 확인되는 필요는 추가 요구의 계획 반영 여부와 기존 작업의 병렬 지속 여부다. 특정 담당자 이름이나 새 TODO·의존성 목록을 보여 달라는 직접 요구로 확대 해석하지 않는다. 이를 보여 주자는 것은 아래 개선 제안이다. 최종 계획·구현 카드가 존재하는 사실과 사용자가 당시 진행 관계를 이해하기 쉬웠는지는 별개다.

체크인 12건 중 model/effort 누락 질문은 2건이며 같은 docs owner의 새 카드에서 발생했다. 이는 재사용한 agent라도 새 task의 최초 보고에 실제 설정을 빠뜨릴 수 있음을 보여준다. 조회·복구 실패, 알림 유실, MCP 성능 저하는 이번 증거로 확인되지 않았다.

고정 로그 파일 덮임과 reviewer의 `git write-tree`에 따른 실제 index 변경도 retro에 있다. 각각 증거 보관·리뷰 절차 문제로 분류한다. Office MCP 오류로 집계하거나 이번 제품 개선 범위에 섞지 않는다.

## 스킬 업데이트 메모

수정 후보는 외부 basic-team의 `references/office-operations.md`와 `references/reporting.md`다. 현재 설치본에는 이미 owner/runtime 구분, 정식 reviewer owner, 첫 보고 readback, 실제 model/effort, 의미 있는 checkpoint 보고가 있으므로 같은 지시를 중복 추가하지 않는다.

- 새 탐색 도구 지원 시 `get_office_rules` → `get_active_runs` → 신규/재개 판단 → 최초 `placements` 확인 순서를 명시하고 미지원 서버의 제한을 설명한다. 이는 021의 기존 권고를 실제 연동으로 이어가는 작업이다.
- 추가 요구 수신 시 기존 작업 지속 여부와 재계획 담당자·TODO 변경을 보고하는 짧은 예시를 넣는다. 런타임 팀 트리를 MCP에 있다고 가정하거나 미지원 필드를 보내지 않는다.
- 같은 actor를 재개해 새 task를 만들 때 실제 설정 전달과 reviewer 정식 이름 일치를 검증하는 예시를 보완한다. owner alias를 대량 허용하는 제품 변경보다 클라이언트 입력을 먼저 바로잡는다.
- 로그 고유 파일명·index 보존 문제는 리뷰/증거 관리 절차의 별도 후보로 남긴다. Office 스킬 지침에 관련 없는 git 작업을 추가하지 않는다.

외부 플러그인 소스·설치 캐시는 이번에 수정하지 않았다. 당시 설치본의 정확한 revision을 확인하지 못했으므로 현재 규칙이 당시에도 같았다고 단정하지 않는다.

## 검증과 한계

실제 pane의 본 인터뷰·후속 답변, 초기·최종 run의 읽기 전용 조회, 회고 신호와 보존 감사, 현재 서버·웹·레지스트리 및 설치 스킬을 대조했다. Office 상태·대상 프로젝트·설정은 변경하지 않았다. 제품 화면 재현과 신규 구현 검증은 수행하지 않았고, API 배정 결과를 화면 확인으로 표현하지 않는다. 문서 로컬 링크와 diff whitespace를 검사했다. 이번 문서만 추가했으며 기존 제품 변경의 테스트 결과를 이번 조사 성과로 재사용하지 않는다. 완료 상태는 조사·정리의 완료이며 개선안의 구현 완료를 뜻하지 않는다.
