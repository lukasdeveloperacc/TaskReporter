실제 마찰은 다음과 같다.

- **집계 카드에 작업자 설정 체크 발생:** owner/model/effort를 의도적으로 비운 REVIEW를 진행중으로 바꾸자 `5aaff6be-c879-4330-8c1d-6bc1bc3730c1` 체크가 생성됐다. 저장된 질문은 model·effort 누락을 요구하며, 답변은 단일 actor가 아닌 승인 집계임을 설명한다. 실제 R1-K/P 카드에는 관측 설정이 있다. 이는 MCP 실패 응답이 아닌 불필요한 확인 왕복이다. 모델을 꾸며 채워 해결해서는 안 된다.
- **첫 작업의 보고 순서:** MOTION은 실제 모델 확인 전에 진행중으로 보고해 `26bdfa84-0522-4bb9-ade5-d3e7494ad4a0` 체크가 발생했다. 이후 turn_context 확인과 같은 task ID patch·check_replies로 해결했다. 이 경우는 집계 예외와 달리 정상 작업자의 초기 보고 순서 개선 대상이다. 두 체크 모두 최신 조회에서 answered다.
- **실행 ID와 owner 혼동:** 상대는 native `/root`에서 직접 `owner: root`를 선택했다고 확인했다. fallback 응답은 봤지만 `leader`와의 좌석 관계는 확인하지 않았다. 실제 서버 배정과 UI도 임시 자리로 일치한다. 부서 알고리즘 오작동보다는 표시 키 선택과 사전 확인 누락이다. `root`를 무조건 `leader`로 바꾸는 전역 별칭은 별도 actor 충돌을 검토해야 하므로 우선안으로 확정하지 않는다.
- **세션에 새 도구 미노출:** 상대가 확인한 ALL_TOOLS는 ask/get_retros/get_run/report 네 개였다. get_office_rules/get_active_runs는 미사용·미노출이라고 답했다. 새 MCP 연결에서는 둘 다 실제 제공돼, 서버 기능 추가만으로 기존 세션에서 바로 쓸 수 있다고 보장할 수 없다.
- **새 run 안내:** 이전 완료 실행 `9bb2e42f-03d9-43a1-a7b6-ab1ad414a2ba`와 이번 실행을 분리했고, 사용자의 “업데이트안해?” 질문 뒤 현재 run 링크를 다시 안내했다고 답했다. 새 요청을 별도 run으로 시작할 때 링크를 즉시 알리는 개선이 적절하다. 이번 조사에서 기존 사용자 탭은 이전 실행 `3f69f9a0-…`를 열고 있었으나, 이것만으로 사용자 혼선의 원인을 단정하지 않는다.
- **Office 밖의 제약:** executor 요청 max와 실제 medium의 차이·리뷰 모델 capacity 재개 경험도 답했으나 Office 오류와 구분했다. `.omx/frontend-actor-settings.json`에는 실제 frontend actor의 sol/luna·medium 값이 있다. 정확한 host 역할 제한 원인까지 이번 조사에서 재현하지 않았다.

## 검증과 한계

실제 pane 인터뷰·sidecar·actor 설정 파일·현재 get_run·새 MCP tools/list와 rules/active-runs 조회·1185px 및 390px 실화면을 대조했다. 조사 탭만 닫았으며 기존 사용자 탭·대상 pane·실제 실행 상태는 변경하지 않았다. 코드 변경이 없어 제품 테스트를 새로 돌리지 않았으며 문서 링크·whitespace를 검증했다. 이전 테스트 결과를 이번 조사 성과로 재사용하지 않는다. 과거 원시 MCP 호출 전체, ask 흐름, 아직 끝나지 않은 실행의 최종 완료·retro는 검증하지 않았다.
