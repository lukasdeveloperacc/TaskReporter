# Office Team Reporter

## 사용자와 목표

Claude Code 터미널에서 basic-team을 실행하는 사용자가 옆 모니터의 로컬 관제실에서 여러 프로젝트의 진행과 결재 요청을 확인한다. 터미널이 주 조종석이며 앱은 에이전트를 직접 실행하지 않는다. 사용자는 회사의 대표이며 화면에 `대표 · 나`로 표시한다. 리더 에이전트는 `부장 · leader`, 다른 에이전트는 부서별 직원으로 표현한다. 이 표시는 역할을 설명하며 에이전트의 owner 식별자는 유지한다. 직원의 모델은 보고된 `task.model` ID와 `effort`를 직접 표시한다. 직급은 선택적인 보조 정보이며 모델명을 대신하지 않는다. 보고되지 않은 모델이나 effort는 추측하지 않는다.

## 제공 범위

1. lukas-plugin `basic-team`(Office 모드)의 첫 report가 저장소 경로를 프로젝트로 등록한다. 프로젝트마다 빌딩 로비의 층이 생긴다. 로비는 지붕·간판, 층별 창과 구조 프레임, 지상 출입구를 갖춘 빌딩 단면도로 표현한다. 층 버튼에서 프로젝트·run·상태를 읽고 사무실로 들어간다. 새 report가 올 때마다 층 번호가 바뀌지 않도록 프로젝트 경로 순으로 층을 배치한다. 보고 갱신만으로 순서는 바뀌지 않지만 프로젝트 추가 시 층 번호는 달라질 수 있다.
2. 층을 선택하면 2D 픽셀 탑다운 사무실에서 직원의 작업, 말풍선, 검수 도장과 라운드를 본다. 모르는 역할은 이름표를 단 임시 자리를 사용한다. `전체 보기`를 열면 사무실 전체가 화면 안에 맞춰져 스크롤 없이 배치를 한눈에 볼 수 있다. 닫으면 기존 픽셀 크기의 일반 보기로 돌아간다.
3. `ask`는 대표실의 결재 서류가 된다. 앱의 선택지가 리더에게 전달되며 미응답 요청은 다음 호출에서도 유지한다. 터미널 답변은 Esc 후 채팅으로 전달하고 리더가 다음 report에서 닫는다.
4. 사용자가 에디터에서 저장소 Markdown을 바꾸면 공지가 나타난다. 다음 report의 diff를 확인한 리더가 재계획 여부를 묻는다. 앱에서는 문서를 읽기만 한다.
5. 완료·중단 run은 업무 일지와 마지막 스냅샷으로 남는다. 30분 무응답은 자리 비움으로 표시하고 새 report로 복귀한다.

직접 둘러보기는 구현·자동 검증·실제 브라우저 검증과 독립 리뷰를 마쳤다. 기존 대표를 방향키·WASD와 화면 버튼으로 움직여 실제 직원의 보고를 살펴보고 엘리베이터로 실제 프로젝트 층을 이동하는 선택 기능이다. 상세 동작과 완료 기준은 [진행 보고와 사무실](requirements/progress-office.md)에 둔다.

## 제품 경계

배포는 localhost 전용 Docker 컨테이너 하나, Node 프로세스 하나와 SQLite named volume을 사용한다. 기본 `~/orca`를 동일 절대 경로로 읽기 전용 마운트한다. 밖의 프로젝트도 층은 만들지만 문서 열람·변경 감지는 제공하지 않는다. 원본 basic-team은 수정하지 않으며 Office 도구가 없거나 연결이 끊기면 기존 progress.py HTML로 폴백한다.

3D, 세션 직접 실행, 원격 접속·다중 사용자, 테마 꾸미기, 효과음, 통계, 앱 내 문서 편집은 v1 범위 밖이다. 개발용 fixture 재생은 검증 도구이며 제품 리플레이 기능이 아니다.

## 근거와 성공 기준

사용자의 13라운드 인터뷰와 승인 계획을 바탕으로 구현했다. 현재 유지보수 기준은 이 문서와 연결된 기능 요구사항이다. 기존 progress.py와 병합 결과가 같고, report→사무실 및 ask→앱 답변→리더의 연결, 문서 변경 공지, 다중 층, 영속 저장이 동작해야 한다. 실제 Claude Code의 긴 ask와 전체 basic-team Office 모드 실행은 SDK fixture 재생과 구분해 검증 결과를 기록한다.
