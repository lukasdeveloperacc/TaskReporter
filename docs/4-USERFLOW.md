# 사용자 흐름

터미널이 실행의 주 조종석이며, 사용자는 앱에서 `대표 · 나`로 표시된다. 별도 로그인·계정·권한 분기는 없다. localhost·origin·문서 경계는 [아키텍처](1-SYSTEM-ARCHITECTURE.md)와 [기획서 요구사항](requirements/documents.md)을 따른다. 현재 별도 `screens/` 시안은 없으며 구현 진입점은 [App.tsx](../web/src/App.tsx)다.

## 시작과 관찰

1. [README](../README.md)의 Docker 및 MCP 연결을 마치고 터미널에서 office-basic-team을 실행한다.
2. 첫 report가 프로젝트와 run을 등록한다. 앱의 `#/` 빌딩 로비에 프로젝트 층이 나타난다. 빈 로비는 첫 보고 대기 안내를 보여준다.
3. 층을 누르면 가장 최근 활성 run으로 진입하고, 활성 run이 없으면 최근 종료 run을 연다. 경로는 `#/run/<run_id>`다. 같은 프로젝트의 활성 run이 여럿이면 선택기로 전환한다.
4. stage·요약·사용자 할 일·막힌 사항과 직원 작업·모델·effort·리뷰를 확인한다. 전체 보기를 열면 사무실 배치를 화면 안에 맞춘다. 닫기·Esc 후 원래 버튼으로 포커스가 돌아간다.
5. 빌딩 로비 버튼으로 프로젝트 선택으로 돌아간다. 자세한 상태 조건은 [진행 보고·사무실](requirements/progress-office.md)에 있다.

## 결정과 변경

대표실 결재 서류 또는 결재 대기 버튼 → 질문·추천 표시 확인 → 선택지 클릭 → 저장·리더 호출 응답 → 창 닫힘 순으로 진행한다. 창만 닫으면 질문은 계속 pending이다. 전송 실패는 창에 표시되고 다시 답할 수 있다. 터미널 답변과 긴 대기 복구는 [결재·실행 연동](requirements/decisions-integration.md)을 따른다.

기획서는 사무실 옆 읽기 전용 패널에서 본다. 에디터에서 수정 → 공지와 열람 내용 갱신 → 다음 report에서 리더가 diff 수신 → 재계획 여부 결재 순으로 이어진다. 접근 불가 경로는 열람·변경 감지 불가로 표시한다.

## 종료와 실패 복구

완료·중단 report → 남은 pending 결재 종료 → 업무 일지 → 해당 run의 마지막 작업·리뷰·결정 스냅샷 열기 순으로 확인한다. 진행 중 30분 무보고는 자리 비움이며 종료가 아니다. 새 report로 복귀한다.

상태 로딩 실패는 오류와 다시 불러오기를 제공한다. SSE 재연결 시 상태를 다시 읽는다. 잘못되거나 존재하지 않는 run 경로는 로비로 표시한다. Office 연결 장애 시 터미널 스킬은 원본 basic-team HTML 진행 화면으로 전환한다. 질문·상태 복원 규칙은 [실행 연동](requirements/decisions-integration.md)에 있다.
